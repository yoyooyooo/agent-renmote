# Whitepaper Compiler Reference

本文件是 `SKILL.md` 的按需参考。每个规则只有一个权威归宿。

# 1. 来源权威

白皮书最大的来源风险，是把会话中的漂亮表达误写成正式决定。先建立权威，再写叙事。

## 1.1 Authority order

从高到低处理冲突：

1. 用户最新且明确的决定、纠正、否定与边界；
2. 用户跨多轮反复表达、没有被撤销的核心期待；
3. 用户明确认可并继续建立其上的方案；
4. 用户提供的正式文档、真实产物与可核验结果；
5. 助手提出但用户尚未确认的提案；
6. 探索性设想、旧实现惯性与已被推翻的细节。

“更新”只有在作用域相同或更广时覆盖旧内容。局部修正不会自动推翻全局原则。

## 1.2 Ledger classes

| Class | Meaning | Whitepaper treatment |
|---|---|---|
| Accepted decision | 用户明确确认的长期决定 | 可写为规范性结论 |
| Stable expectation | 多轮稳定存在、未被撤销的核心期待 | 可写为原则，措辞保持克制 |
| Accepted proposal | 助手提案被用户明确接受并继续采用 | 可写为规范性结论 |
| Candidate | 有吸引力但尚未确认 | 标为候选或开放问题 |
| Implementation fact | 当前代码、架构、流程或产品现状 | 解释现状，不定义永久身份 |
| Observed result | 测试、数据、真实使用或评估结果 | 可支持判断；保留范围与时间 |
| Superseded | 被更新决定覆盖 | 从正文移除；必要时进入变更记录 |
| Open question | 材料不足或仍有真实分歧 | 放入开放问题，不替项目作决定 |

内部账本可以使用：

```yaml
statement:
class:
scope:
authority_source:
time:
evidence_location:
conflicts:
resolution:
whitepaper_destination:
```

## 1.3 Normative admission test

一个陈述只有满足下列之一，才可成为“必须”或“应当”：

- 有 Accepted decision；
- 有 Stable expectation，且未与后续决定冲突；
- 有 Accepted proposal；
- 它是核心承诺成立所不可缺少的逻辑约束，并在正文中解释推导。

实现方便、当前技术限制、行业惯例与助手偏好不足以单独成为永久原则。

## 1.4 Conflict handling

- **Direct correction**：采用最新明确修正。
- **Scope conflict**：分别保留全局与局部结论，写清适用范围。
- **Value–implementation conflict**：价值与长期期待优先；当前实现进入现状差距或非规范示例。
- **Unresolved trade-off**：保留两侧约束，进入开放问题或实现分支。
- **Evidence conflict**：保留冲突、范围与不确定性，不合成为伪共识。

## 1.5 Claim ceiling

- 目标不等于已实现；
- 代码存在不等于产品价值已验证；
- 一次成功运行不等于长期可靠；
- 多人转述不等于独立证据；
- 用户行为不等于用户意图；
- LLM 生成不等于正式知识。

# 2. 白皮书契约

## 2.1 Document identity

白皮书是项目的上位产品与技术宪章。它定义项目为何存在、创造何种价值、如何理解自己的领域、拥有哪些能力与权威边界，以及不同实现如何仍属于同一项目。

| Document | Governs |
|---|---|
| Whitepaper | 身份、价值、不变量、语义、能力、边界、评价、符合性 |
| PRD | 特定版本的用户问题、范围、功能与验收 |
| Architecture | 组件、存储、协议、部署与非功能设计 |
| ADR | 一项具体决策及其权衡 |
| Roadmap | 顺序、阶段、里程碑与资源 |
| Operations | 安装、运行、监控与恢复 |
| Marketing | 面向市场的定位与传播 |

## 2.2 Required outcomes

完整白皮书使读者能够回答：

1. 项目是什么，以及不是什么；
2. 它为什么值得存在；
3. 它的价值单位是什么；
4. 哪些长期原则不能被实现便利破坏；
5. 它怎样抽象自己的领域；
6. 价值如何从输入流转到结果；
7. 用户最终感知到什么；
8. 系统必须具备哪些能力；
9. 智能、自动化、用户与外部执行者各自拥有什么权威；
10. 怎样评价效果、可靠性与经济性；
11. 合理上限、非目标与失败边界是什么；
12. 不同实现如何声明符合性。

## 2.3 Normative vocabulary

- **必须 / 不得**：Core Conformance 的硬约束。
- **应当 / 不应**：默认约束；偏离需要说明理由与影响。
- **可以**：实现自由。
- **候选**：尚未成为正式状态。
- **正式状态**：经过规定规则或治理后生效。
- **非规范示例**：帮助理解，不约束实现。

规范词保持稀缺。每个“必须”都应指向项目身份、信任边界或关键价值。

## 2.4 Value unit

活动量不是价值。项目必须定义一种可由用户、业务或研究结果验证的价值单位，例如：

- 被接受的认知变化；
- 被避免的故障；
- 被缩短的决策时间；
- 被正确完成的高风险操作；
- 被复用的可信知识；
- 被转化为实践的洞察。

处理条数、生成字数、任务数量、模型调用量与工作流成功数只能作为运营指标。

## 2.5 Architecture neutrality

正文通过以下测试：

- 移除当前编程语言后仍成立；
- 更换数据库、UI、部署方式、模型、供应商与运行时后仍成立；
- 页面、命令、报告、中间产物与表结构没有成为永久领域对象；
- 具体技术被标为当前选择、适配器或非规范示例；
- 不同实现共享相同语义、权威、质量与价值约束。

架构中立不是无限宽松。实现自由发生在共同不变量之下。

## 2.6 Core concept test

核心概念应当：

- 在多个实现分支中仍有意义；
- 能解释项目如何理解世界；
- 有稳定身份、关系、时间或权威；
- 不依赖当前 UI 或数据表名称；
- 能支持价值链与治理。

临时批次、工作流步骤、页面组件、报告版式与供应商对象通常属于实现层。

## 2.7 Capability contract

每项核心能力至少说明：

```yaml
purpose:
input:
output:
success:
evidence:
abstention:
authority:
forbidden_effects:
```

能力优先于工作流。多个工作流可以实现同一能力，同一工作流也可以组合多项能力。

## 2.8 Conformance

建议使用三级声明：

- **Core Conformance**：遵守项目身份、核心语义、权威边界、证据要求、可修订性与最低质量门禁。
- **Experience Conformance**：在 Core 之上，兑现主要用户价值与核心任务。
- **Full-loop Conformance**：在 Experience 之上，形成反馈、学习、修订、治理与长期评价闭环。

实现可以声明部分等级，但必须准确列出尚未满足的条款。

## 2.9 Time horizon and open questions

白皮书以三到五年为默认时间尺度。容易在一个版本内变化的内容进入 PRD、架构、ADR 或路线图。

开放问题只保留真正尚未决定、会影响长期方向的事项。每项说明：为什么重要、已知约束、当前缺少什么、哪类决定将使其关闭。

# 3. 叙事架构

白皮书采用演绎叙事。会话时间线只用于判定权威，不用于组织正文。

## 3.1 Canonical arc

1. 文档定位；
2. 执行摘要；
3. 使命与品类；
4. 第一性原理；
5. 产品或项目宪章；
6. 用户与核心任务；
7. 核心概念模型；
8. 领域语义；
9. 生命周期；
10. 体验投影；
11. 核心能力；
12. 智能与自动化；
13. 信任与治理；
14. 评价与经济性；
15. 上限与非目标；
16. 反模式；
17. 架构中立与实现分支；
18. 符合性；
19. 版本与长期演化；
20. 结语。

## 3.2 Adaptive branches

- **Product**：强化用户、核心任务、体验投影、反馈闭环、价值指标与边界。
- **Platform / framework**：强化参与者、扩展点、协议语义、兼容性、治理、生态与分层符合性。
- **Protocol / standard**：强化术语、状态机、互操作、规范词、测试套件、安全模型与版本演化。
- **AI / research system**：强化证据层级、模型权威、弃权、评测集、漂移、成本、可重放与人工治理。
- **Internal operating system**：强化组织角色、决策权、输入输出、责任交接与控制点。

章节可以重命名或合并，但每个必答问题只能有一个权威归宿。

## 3.3 Paragraph grammar

强段落通常按以下顺序：

1. **结论** — 本段要求什么；
2. **理由** — 为什么对项目价值必要；
3. **约束** — 它排除了哪些误解；
4. **影响** — 对能力、体验或实现意味着什么。

首次引入核心术语时，同时说明：它是什么、不等于什么、与相邻概念的关系、时间/证据/权威属性，以及一个简短的非规范示例。

## 3.4 Transformations

### Implementation → invariant

材料：“我们用 Issue 驱动任务，Autopilot 定时跑 CLI。”

编译：“后台执行机制应当与核心领域状态解耦；调度器、任务载体与 Agent Runtime 是可替换的执行适配器。”

### Feature → value principle

材料：“首页每天展示五张卡片。”

编译：“产品应当以有限注意力预算呈现少量高价值变化，并允许在价值不足时保持安静。卡片数量属于体验实现选择。”

### Current storage → semantic object

材料：“系统有 dossier、manifest、report 三种 JSON。”

编译：“派生材料应当保留从证据到正式状态的可追溯关系；阅读投影不是独立事实权威。中间产物与序列化格式由实现决定。”

### Workflow → capability

材料：“晚上运行 dreaming，早上生成 digest。”

编译：“系统必须具备周期性整合、状态重评估与面向用户的变化投影能力。触发时间、批处理与工作流数量属于实现自由。”

### Ambition → bounded promise

材料：“最终希望自动形成正确的长期知识。”

编译：“系统可以提出长期认知修订候选，并保存证据、版本与撤销路径；高影响更新的自动提交范围必须由质量证据和治理策略决定。”

# 4. 质量门禁

以下为阻断门禁。任一失败都应先修订，再交付。

## G1 — Identity

- 有一句话定义与一句话核心承诺；
- 项目品类清楚；
- 定义不依赖当前技术栈、页面或供应商。

## G2 — Value

- 明确价值单位；
- 价值指标指向用户、业务或研究结果；
- 活动量仅作为运营指标。

## G3 — Authority

- 规范性主张有可解释的权威；
- 最新明确决定覆盖旧设定；
- 未确认的助手提案仍是候选；
- 已推翻内容没有在正文中复活。

## G4 — Constitution

- 原则具有行为约束，而非口号；
- 每条原则说明它排除什么设计；
- “必须”数量克制，并对应身份或信任边界。

## G5 — Semantics

- 核心对象定义了“是什么”与“不是什么”；
- 事实、推断、候选、正式状态与外部效果被区分；
- 时间、版本、证据与权威在需要处被说明。

## G6 — Lifecycle

- 从输入到价值的完整流转清楚；
- 有失败、弃权、修订、撤销或重新评估路径；
- 高层投影能够回到低层依据。

## G7 — Intelligence

- AI、LLM、Agent 或自动化职责具体；
- 模型输出不会自动成为事实或用户意图；
- 证据不足时允许不确定、弃权或人工接管；
- 高影响动作有治理边界。

## G8 — Architecture neutrality

- 语言、数据库、客户端、部署、模型、检索与运行时可替换；
- 当前实现仅作为非规范示例或实现分支；
- 工作流、报告、页面与表结构没有偷渡为永久概念。

## G9 — Evaluation

- 技术质量、用户价值、可靠性与经济性分别有评价方式；
- 指标能够发现“运行成功但没有价值”；
- 未验证收益使用条件性语言。

## G10 — Limits

- 区分高置信可达、有条件可达与不承诺；
- 输入上限、观察盲区与自动化风险清楚；
- 非目标真实约束范围。

## G11 — Conformance

- 不同实现分支可以声明共同符合性；
- 最低不变量可检查；
- 偏离能够被记录，而不是被措辞掩盖。

## G12 — Editorial integrity

- 每个重要观点只有一个权威归宿；
- 章节按演绎关系推进；
- 术语稳定，例子标为非规范；
- 开放问题与正文结论分开；
- 文档没有未处理占位符、断链与相互矛盾的规范词。

# 5. 常见失败与修复

| Failure | Symptom | Repair |
|---|---|---|
| Transcript whitepaper | 按讨论时间线叙述 | 用权威账本解决历史，只呈现当前宪章 |
| Architecture smuggling | 当前组件成为核心概念 | 提升为语义对象、能力或适配器职责 |
| Feature constitution | 原则实际是功能列表 | 回到长期价值与约束 |
| AI incantation | “AI 自动分析”代替能力定义 | 写清输入、输出、证据、弃权与权威 |
| Consensus laundering | 热度或转述被写成事实 | 分开社会状态、独立证据与事实真伪 |
| Metrics theatre | 用处理量证明价值 | 绑定价值单位 |
| Persona fiction | 点击被写成明确偏好 | 区分 observed、inferred 与 explicit |
| Promise inflation | 目标、代码与长期能力混同 | 应用 claim ceiling |
| Principle wallpaper | 原则不改变任何设计 | 增加具体约束与反模式 |
| Sediment | 为兼容旧讨论保留失效内容 | 删除被覆盖内容，历史进入版本记录 |
